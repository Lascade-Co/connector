# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Multi-platform ETL pipeline system that extracts marketing/analytics data from 5 advertising platforms and loads into ClickHouse. Built on Python 3.12 with [dlt](https://dlthub.com/) as the core ETL framework.

**Data Sources:** Facebook Ads, Google Ads, Google Analytics 4, Google Play Console, App Store Connect, eSIM Analytics API
**Data Destinations:** ClickHouse `travel` (primary), ClickHouse `esim_db` (esim project), PostgreSQL (replication source)

## Commands

### Run a pipeline locally
```bash
# Pattern: python main.py <platform> <group>
python main.py facebook d1c
python main.py google g1
python main.py google_analytics ga1
python main.py google_play gp1
python main.py app_store as1
python main.py pg dashboard

# eSIM pipelines (destination: clickhouse_esim → esim_db)
python main.py esim default
python main.py esim_facebook d1c
```

### Install dependencies
```bash
pip install -r requirements.txt
```

### Local infrastructure
```bash
docker-compose up -d          # Start ClickHouse + PostgreSQL
docker-compose --profile metabase up -d  # Include Metabase
```

### Backfill mode
Set environment variables before running:
```bash
FB_BACKFILL_DAYS=90 python main.py facebook d1c
GA4_BACKFILL_DAYS=30 python main.py google_analytics ga1
ESIM_FB_BACKFILL_DAYS=90 python main.py esim_facebook d1c
```

## Architecture

### Entry Point & Dispatch
`main.py` → dispatches to `pipelines/<platform>/<platform>_pipeline.py` based on CLI args.

### Pipeline Structure
Each platform follows the same pattern:
1. **Pipeline runner** (`pipelines/<platform>/<platform>_pipeline.py`) — reads group config, creates dlt pipeline, executes sources
2. **Sources** (`pipelines/<platform>/sources.py`) — dlt resource definitions that transform API data into tables
3. **Group config** (`secrets/<platform>.json`) — JSON files defining account groups with credentials/tokens

### Custom dlt Sources (Modified from dlt verified sources)
- `facebook_ads/` — Custom Facebook source with incremental creative reconciliation, quota telemetry, bounded async Insights windows, and action metrics decomposition
- `google_analytics/` — Custom GA4 source with helper utilities
- `google_ads/` — Google Ads client integration

### Key Modules
- `utils.py` — Shared helpers: `get_for_group()` (loads group config with account_ids), `load_config()` (loads group config without account_ids assumption), date normalization, logging setup
- `facebook_ads/helpers.py` — Insights async job polling, explicitly API-bound account clients, and action metrics flattening
- `facebook_ads/settings.py` — Field definitions, insight breakdowns, action type selections

### Group-Based Account Management
Accounts are organized into named groups (d1, m4, d2, d1a, d1b, d1c, etc.). Each group:
- Has its own credentials in `secrets/<platform>.json`
- Maintains isolated dlt pipeline state (pipeline name includes group suffix)
- Runs independently in GitHub Actions

### Data Loading Patterns
- **Merge disposition** with primary keys for upsert behavior (most pipelines)
- **Replace disposition** for full-refresh tables
- dlt handles ClickHouse schema creation and evolution automatically
- Dataset/table naming uses configurable separators
- dlt merges emit `DELETE FROM`, which ClickHouse runs as a synchronous mutation. It must stay synchronous: the delete's `IN (SELECT ... FROM <temp>)` subquery is evaluated when the mutation runs, and dlt drops that temp table as soon as the statement returns
- ClickHouse 25.12 crashes vertical merges on tables carrying lightweight deletes (`Code: 295 ... ColumnGathererTransform (RECEIVED_EMPTY_DATA)`). The failed merge retries forever, and because the scheduler picks merges before mutations, every pending delete starves — the pipeline then hangs in `waitForMutation` until the socket dies. Any dlt merge table over 131k rows with 11+ non-PK columns is exposed; fix with `ALTER TABLE <t> MODIFY SETTING enable_vertical_merge_algorithm = 0`. Diagnose via `system.part_log` where `error = 295`
- **dlt retries can double-insert, because plain `MergeTree` does not deduplicate inserts by default.** `raise_on_max_retries = 2` lets dlt retry a load job once; when the first INSERT times out client-side but completes server-side, the retry writes a second, byte-identical copy (same `_dlt_id`, same `_dlt_load_id`). This hit the Insights family 12 times between 2026-03 and 2026-11 (291 rows / 31,425 AED in `fb___insights`, 7,524 rows in `__actions`). Fix: `ALTER TABLE <t> MODIFY SETTING non_replicated_deduplication_window = 1000`, which makes ClickHouse ignore a repeat of a recently inserted block — set on all six original `fb___insights*` tables. The two newer nested tables `fb___insights__conversions` and `fb___insights__conversion_values` need this setting **and** `enable_vertical_merge_algorithm = 0` right after their first load, making eight in total — they fan out several child rows per ad-day, so they cross the 131k-row exposure quickly. `fb___insights__cost_per_result` is outside that set and currently carries neither this setting nor `enable_vertical_merge_algorithm = 0`. **Audited 2026-11-05 against `system.tables`: four tables still carry neither setting** — `fb___insights__conversions` (4,328 rows), `fb___insights__conversion_values` (4,182), `fb___insights__cost_per_result` (25,055) and `fb___insights_country` (**137,173 rows, 26 non-PK columns — already past the 131k Code-295 exposure threshold**, despite the rollout note below saying to ALTER it as soon as it appeared). `system.part_log` shows no `error = 295` in the preceding 14 days, so it has not bitten yet. `cost_per_result` already carries **47 duplicate `_dlt_id` groups**, the double-insert signature, which is what the missing dedup window predicts. The six original tables are confirmed to have both settings. The deduplication window matches on block fingerprints, so a retry that splits data into different blocks could still slip through; check with `SELECT _dlt_id FROM <t> GROUP BY _dlt_id HAVING count() > 1`. Clean up with `OPTIMIZE TABLE <t> FINAL DEDUPLICATE BY _dlt_id` — `DEDUPLICATE BY` must also list every sorting-key column (`fb___insights` needs `_dlt_id, date_start, ad_id, account_id`). **Never run it on `fb___insights__cost_per_action_type`**: it holds 154,564 orphan rows with empty `_dlt_id` that it would collapse into one; that table still carries 4,159 duplicate groups pending a decision on the orphans

### Rate Limiting & Scaling
- Facebook A/B/C matrices mix independent `d1`/`m4`/`d2` families, spacing each family's suffix shards by roughly one hour; account delays default to zero
- Insights use separately committed async date windows, 100-row result pages, and split incompatible unique metrics; quota failures surface without stacked retries
- The travel `facebook` pipeline skips unused creative enrichment; keep Insights, ads, campaigns, ad sets, and FX processing. Existing creative tables/state are retained. eSIM/subscription creative refreshes remain enabled.
- Partial current-state loads commit valid merges; later reconciliation repairs only the missing subset
- Daily Insights expose trial and subscription counts and values as four scalar columns merged by `action_type` across `conversions`/`conversion_values` and `actions`/`action_values`, the conversions arrays taking precedence for the same type. Travel and subscription request the conversions arrays; eSIM does not, so eSIM `subscriptions` stays 0. On travel, `trial_starts`/`subscriptions` were 0 on every row of the prior 90 days (38.5k rows) before the conversions arrays were requested, so history before that deploy stays 0 unless backfilled with `FB_BACKFILL_DAYS`. **Older than that the columns are NULL, not 0, and the distinction breaks MBQL measures.** The columns were only added on 2026-07-26: as of 2026-11-05, 125,068 of 166,508 `fb___insights` rows have `trial_starts IS NULL`, 39,675 hold a real 0, and only 1,765 are positive (all from 2026-10-26, when the conversions arrays went in). ClickHouse `sum()` over an all-NULL group returns NULL, and `NULL + x = NULL`, so any measure that adds a trial sum to another sum blanks out entirely on pre-2026-07-26 days unless **every additive term** is wrapped in `coalesce(..., 0)` — denominators included. Metabase wraps only the outer denominator in `NULLIF(..., 0.0)`, which guards zero and not NULL, so it will not save you. Questions 611 and 997 do this correctly; copy their shape; rows loaded between that deploy and the `*_total`/`*_website` alias fix hold app-only undercounts; the 7-day reload repairs only days still inside its window, and anything older needs `FB_BACKFILL_DAYS`
- **Subscribe lives only in the conversions arrays.** Meta never puts Subscribe in `actions`. Travel requests `conversions`/`conversion_values` (dlt child tables `fb___insights__conversions`/`__conversion_values`); `conversion_values` is AED-converted in place pre-flatten like `action_values`, `conversions` are counts and are not converted. The scalars `subscriptions`/`subscription_value`/`trial_starts`/`trial_start_value` resolve via `_SUBSCRIPTION_EVENT_ALIASES`/`_TRIAL_EVENT_ALIASES` to Meta's rollup (`omni_*` first, then `subscribe_total`/`start_trial_total`), else one app + one web component (web includes `subscribe_website`/`start_trial_website`), so they agree with model 587's `subscribe_total`/`start_trial_total` — except when an `omni_*` rollup is also reported (it wins, from `actions`; travel `actions` carries no subscribe or trial entries today) or Meta repeats an entry (scalars keep the first, the model sums; see the next bullet). Travel subscribes and trials are mostly **website** events: the first m8 load showed `subscribe_total` 37 = website 29 + app 8, and `start_trial_total` 4,982 all website. Before the aliases knew `*_total`/`*_website` the scalars missed them — subscriptions 8, subscription value 0, trials 0. Never add `subscribe_mobile_app` on top of `subscribe_total`: that double counts. `conversions` also carries `offsite_conversion.fb_pixel_custom.*` rows (lead-form fields), so always filter by exact `action_type`
- The `insights__actions`, `insights__action_values`, and `insights__website_ctr` nested tables are read directly by the Metabase model `fb_insights_base_data` (id 587). Do not stop populating, truncate, or drop them. `insights__conversions` and `insights__conversion_values` are on this list too: model 587 reads `subscribe_total` and `start_trial_total` from them. The flattened scalar columns are not a substitute: `_expand_action_list` keeps the first entry per `action_type` while the model sums them, and Meta returns repeat entries often enough that ~4% of rows disagree
- Facebook historical backfills load Insights only and serialize multi-group matrices; current-state resources use the daily/manual Facebook workflows

### Degraded Insights reports (all three Facebook pipelines)
On 2026-10-21 Meta returned `Job Completed` Insights reports whose **absolute** delivery counts were zeroed — `spend`, `impressions`, `clicks` all `"0"`, `reach` absent — while the **derived ratios** (`ctr`, `cpc`, `cpm`) and the action arrays stayed correct. dlt merged those rows over good ones, destroying 2026-10-13..10-20 for M4 - Hotel and three other accounts. Because each run only reloads a 7-day attribution window, the oldest day of each window is written once and never revisited, so a single bad report permanently burns that day.

- `degraded_report_rows` in `facebook_ads/insights.py` refuses the report. A row is degraded when `impressions` is **reported as** zero alongside a positive `ctr`/`cpc`/`cpm`, or `clicks` is reported as zero alongside a positive `ctr`/`cpc`. One such row is enough: `ctr = clicks/impressions*100`, `cpm = spend/impressions*1000` and `cpc = spend/clicks`, so each zeroed count is paired only with the ratios it divides.
- **`cpm` is deliberately paired with `impressions` alone.** An ad that served impressions and got no clicks legitimately reports `clicks=0` with `cpm>0` — 1,946 such rows existed in production when this was written — so pairing `clicks` with `cpm` would hard-fail normal daily windows. A test named for that consequence locks it in.
- **Only a count Meta actually reported as zero counts.** Absent, `None`, `""` and non-numeric values never satisfy the zero test, so requesting the ratios without `impressions`/`clicks` cannot make every row look degraded.
- A degraded window is **re-fetched once** before raising, since the fault is per-request and each submission creates its own async job. A retry that is still degraded **or came back with fewer rows** raises — a short retry was never validated either, so it must not pass as a recovery and advance the checkpoint. A retry re-runs both the core and unique jobs, each bounded by `FB_INSIGHTS_MAX_WAIT_TO_START_SECONDS` (300) plus `FB_INSIGHTS_MAX_WAIT_TO_FINISH_SECONDS` (3600), so a retried window can cost ~2 hours against the 6-hour runner ceiling.
- A successful retry logs a **warning only**. `_reusable-etl.yml` alerts Slack on `if: failure()`, so a self-healed window is visible in the Actions log but is **not** alerted. If Meta starts degrading reports at scale, that shows up as retry warnings nobody is paged for — promote these to a Slack signal if it ever becomes routine.
- The raise happens **before** the `yield` and the window checkpoint is set **after** it. That ordering is what guarantees nothing from a bad window reaches dlt and that the checkpoint cannot advance past it — do not reorder. A raise discards only the current window because `run_insights_in_windows` always passes an explicit `report_start_date`/`report_end_date`, which collapses the source's own window loop to a single iteration. The source's default (`report_start_date=None`) still iterates many windows per run, so that single-window guarantee is a property of the runner, not of the source.
- **A degraded account is parked, not fatal.** `run_insights_isolated` in `pipelines/facebook/runner.py` wraps the per-account Insights load: it marks the account through `mark_partial_resource(INSIGHTS_RESOURCE, …)` and lets the loop continue. It **returns nothing** — parking is observable only through `get_partial_resources()`, so no caller can branch on it. That account's current and all remaining Insights windows are abandoned; its current-state resources, the remaining accounts and `raise_for_partial_resources` all still run (plus the travel-only `_record_fx_rates` audit write), so the job still exits non-zero and the Slack alert fires.
- **Two kinds of parking share one registry, and only one of them is a quota signal.** `account_has_quota_parking` in `creative_status.py` answers "is Meta throttling this account", and `run_structural_resources` breaks out on it. A degraded Insights report is a report-generation fault, so it is listed in `NON_QUOTA_RESOURCES` and that predicate ignores it — otherwise a degraded account would stop refreshing its campaigns, ad sets, ads, budgets and bids for as long as Meta kept degrading it, silently. Add any future non-quota mark to that frozenset. One registry rather than two, because a second one means a second reset every pipeline must remember to call, and because the combined failure message naming `ads: act-y; insights: act-x` (sorted by resource) is useful.
- **The cost of still loading current state for a degraded account** is that account's full set of structural paging calls, which previously did not happen at all — plus, on travel, one `_fetch_account_currency` call, because a degraded account yields no Insights rows for `note_account_currency` to read a currency from (the documented fallback below, now reachable one more way). Those calls drive the utilization that makes `observe_meta_response` sleep up to `FB_RATE_LIMIT_MAX_PACE_SECONDS` (30s) per response at or above `FB_RATE_LIMIT_PACE_THRESHOLD` (90%). Combined with a ~2h degraded retry this brings the 6h runner ceiling closer — and a job killed by that ceiling is *cancelled*, which `if: failure()` does not catch. If that ever bites, load current state *before* Insights per account: it banks the cheap always-loadable resources first and sidesteps the currency fetch too.
- **During a backfill** (`FB_BACKFILL_DAYS` and friends) current-state resources are skipped anyway, so the split is a no-op there — but a degraded window still aborts that account's *remaining* backfill windows and still fails the run at the end.
- **The caller never sees `DegradedInsightsReport` directly — unwrap `__cause__`.** `pipeline.run` wraps anything escaping extraction in `PipelineStepFailed(...) from exc` (`dlt/pipeline/pipeline.py`), so a plain `except DegradedInsightsReport` around `run_insights_in_windows` silently never fires. `find_degraded_cause` walks both `__cause__` and the `PipelineStepFailed.exception` carrier, mirroring `find_rate_limit_cause` in `pipelines/facebook/rate_limit.py`. A non-degraded cause is re-raised, so ClickHouse timeouts and `InsightsJobFailed` keep today's abort behaviour — **only** `DegradedInsightsReport` is isolated. Note `PipelineStepFailed(...)` constructed directly does *not* set `__cause__`; a test that skips the `raise ... from` chaining exercises only half the path.
- **Why parking cannot leak the bad window — and the reason is narrower than it looks.** The guard raises *before any row is yielded* and before the `INSIGHTS_WINDOW_CHECKPOINT` write, so no data file was written and the incremental's persisted `last_value` never advanced. The safety is "nothing was written", **not** per-run storage isolation: `extract()` calls `create_load_package(..., reuse_exiting_package=True)`, which deliberately hands the next extract the *same* uncommitted package folder left by the failed one. A structural `pipeline.run` now follows immediately after every degraded failure, last account in the group included, so that reused package is committed by an unrelated resource within the same run. Making the Insights source yield rows page-by-page before validating would therefore let a parked window's rows commit — and every test would still pass. Do not weaken the before-`yield` ordering on the assumption that storage isolates windows.
- **What parking gives up:** the failure now surfaces only at end-of-run, from a process-local registry. Anything that kills the process first — OOM, runner eviction, the 6h ceiling — loses the report, and a job killed by the GitHub timeout is *cancelled*, for which `if: failure()` does **not** fire, so that tail is silent.
- **Blind spot:** a *fully* zeroed report — absolutes zeroed **and** ratios absent — passes silently and still overwrites good rows. The ratio check is a sentinel, not a proof of health; a green run does not mean Meta's report was complete. A window that legitimately returns **no rows at all** is also indistinguishable from one Meta dropped, and advances the checkpoint.
- Unexplained and warning-only: in the same incident 100% of rows had NULL `reach` even though the unique-metrics job returned several result pages, so it was not an empty report. `unique_metrics_missing_despite_delivery` logs a warning when a window shows delivery but no row carries any of `reach`/`frequency`/`unique_clicks`/`unique_ctr`/`cpp`. It never raises, because the mechanism is not understood.

### Facebook currency normalization (travel `fb` dataset only)
Not every Facebook account bills in AED, but Metabase compares them as if they did. `pipelines/facebook/currency.py` restates every monetary value in AED **in place**, so `spend`, `cpc`, `cpm`, `cpp` and the nested `value` columns stay AED and **no Metabase consumer needs a currency change**. Verified consumers reading `travel.fb___insights` directly: model 587 `fb_insights_base_data`, and questions 601, 603, 948, 367.

- **The source currency comes from Meta, not from config.** `pipelines/facebook/raw_sources.py` adds `account_currency` to the requested Insights fields, so each row states its own currency. There is deliberately no per-account currency map to keep in sync. `secrets/facebook.json` needs no currency key.
- **Conversion runs pre-flatten.** `facebook_insights_source(pre_flatten=...)` applies the map *before* `flatten_facebook_insights`, so every scalar derived from a nested array (`action_values_*`, `cpa_*`, `trial_start_value`, `subscription_value`, `cost_per_result`) inherits AED without being enumerated. Do not move this after flattening.
- **Two destination type families, and each is written back as it already is.** `spend`/`cpc`/`cpm`/`cpp` and every nested `value` are `Nullable(String)` — write `str(Decimal)`. The flattened scalars (`action_values_*`, `cpa_*`, `cost_per_result`, `trial_start_value`, `subscription_value`) are `Nullable(Float64)` and Metabase renders them as numbers — they must stay Float64. Arithmetic is `Decimal` throughout, quantized at six places.
- **`INSIGHT_FIELDS_TYPES` hints are dead for existing columns.** It hints `spend` as `decimal` while the live column is `String`; dlt never retypes an existing column. Never assume adding a hint took effect — check the live type.
- **The attribution-window columns are money too.** `insights__action_values` and `insights__cost_per_action_type` carry `_1d_click`/`_7d_click`/`_28d_click`/`_1d_view`/`_7d_view`/`_28d_view` alongside `value`, populated in 93–99% of rows. All are converted (matched by shape, so a new window Meta adds is covered). Converting only `value` would leave one row holding two currencies.
- **Not converted, deliberately:** `purchase_roas` (value and spend share a currency, so the ratio is invariant), `ctr`/`unique_ctr`/`frequency`/`website_ctr`, and all counts (`impressions`, `clicks`, `reach`, `actions_*`, `trial_starts`, `subscriptions`).
- **The rate travels on the row.** Every row carries `source_currency`, `reporting_currency`, `fx_rate_to_aed`, `fx_requested_date`, `fx_effective_date`, `fx_rate_status` and `spend_source`. Nested entries keep `value_source`. Because the rate used is denormalized, `fb___fx_daily_rates` is an **audit record, not a dependency** — Insights never reads it back, so there is no cross-table atomicity problem to solve. If a rate cannot be resolved the map raises, the window's `pipeline.run` fails, nothing commits and the checkpoint does not advance.
- **Rates come from the ECB, cross-multiplied through the USD/AED peg:** `aed_per_gbp = (usd_per_eur / gbp_per_eur) * 3.6725`, both legs joined on `TIME_PERIOD` because the API groups rows by series, not by date. `fx_rate_status` is `exact` when the day was published, `carried` when a later observation proves the ECB moved past a non-publication day (final), and `provisional` when it may still be restated — the 7-day attribution reload settles those. A rate more than 4 days old warns; more than 7 days old fails the window closed.
- **An AED account short-circuits before any network call** and its stored strings stay byte-identical, so "no ECB request occurred" is a meaningful canary check. This is why the identity path skips the arithmetic instead of re-quantizing.
- **This is a reporting rate, not the ledger cost.** Meta bills GBP accounts in GBP; the real AED cost includes the card/bank FX spread (typically 1–3%), so GBP spend will not tie to finance's books.
- **Budgets are minor units.** `daily_budget`/`lifetime_budget` (text) and `bid_amount` (Int64) are converted with the same rate — AED and GBP are both two-decimal currencies, so no unit adjustment is needed — and rounded back to whole minor units. The account currency here comes from what Insights already reported; Meta is asked only for an account Insights returned no rows for.
- **Scoped to travel.** eSIM and subscription Facebook pass no `pre_flatten` and no `row_transform`, so their behavior and columns are unchanged. `DEFAULT_INSIGHT_FIELDS` was deliberately not modified; travel's own additions live in `INSIGHT_FIELDS` in `pipelines/facebook/raw_sources.py`.
- Local Facebook, eSIM Facebook, and subscription Facebook execution is restricted to exact group `d1c`; all other groups are GitHub Actions-only
- Max parallel: 1 per batch in GitHub Actions
- **Scheduled runs alert on failure.** `_reusable-etl.yml` ends with an `if: failure()` step that posts the pipeline, group, and run URL to `SLACK_WEBHOOK_URL`. It is **inert until that repo secret is set** (logs a skip and exits 0) and ends in `|| true`, so a Slack outage can never mask the real ETL failure. Before this existed nothing announced a broken run — the hourly eSIM sync failed silently for as long as it took someone to open the Actions tab.
- **`tests.yml` runs `python -m unittest discover -s tests -t .`** on push to `main`, PRs, and manual dispatch. The repo previously had no test workflow at all, so `tests/` only ran by hand. Test modules import `dlt`/`facebook_business` at module scope, so the job installs the full `requirements.txt` — a partial install surfaces as collection errors, not failures.

### Facebook delivered-country Insights (travel `fb___insights_country`)
Campaign × day × **delivered** country (Meta's `country` breakdown), built so dashboard 73 can stop assigning multi-country ad sets to `MULTI`. Travel only; eSIM and subscription Facebook are unchanged.
- **Separate dlt pipeline, same dataset:** `fb_ads_country_<group><suffix>` writes `travel.fb___insights_country`. Separate because the Insights window checkpoint is keyed on `facebook_insights_<account_id>` under source `facebook_ads`, so a second feed inside `fb_ads_<group>` would share — and corrupt — the main feed's checkpoint. It has its own `sync_destination()`; without it every GitHub run would start from empty state and reload the full first-load window.
- **Runs after the per-account loop**, so a country failure cannot stop any account's main Insights or current state. **Any** country failure for an account — degraded window, timeout, quota, FX — parks only that account under `insights_country` (in `NON_QUOTA_RESOURCES`), not `insights`; the remaining accounts, `_record_fx_rates` and `raise_for_partial_resources` still run, so main-feed parking is never masked and the job still ends red. `FB_ACCOUNT_DELAY_SECONDS` is deliberately not applied between country accounts (it defaults to 0).
- **First load is 92 days** (`COUNTRY_INITIAL_LOAD_DAYS`), covering question 1001's 91-day window with no manual backfill. **Skipped entirely under `FB_BACKFILL_DAYS`**, so backfills stay Insights-only — and therefore country history older than the first load needs a code change (e.g. a dedicated backfill env); gaps from outages self-heal from the checkpoint. `country_pipeline.sync_destination()` still runs during a backfill; that is one harmless round trip.
- **Breakdown dimensions are row identity.** `merge_report_rows`/`report_row_key` take `breakdown_fields`; without them every country of one campaign-day collapses into a single row (last wins). That is the real collapse hazard. The inner resource's `primary_key` also gains the breakdown, which matters only in dlt's rare boundary dedup (a row dated exactly the window start whose hash was saved by the previous run). The default preset has no breakdowns, so the three existing feeds send byte-identical requests. `facebook_insights_source` had its `breakdowns` request key commented out, so before this no preset other than the default ever worked.
- **Fields are `ctr` only, never `cpc`/`cpm`/`cpp`.** `_COUNT_RATIO_PAIRS` pairs `spend` with those, and tiny per-country slices can round spend to `"0"` beside a positive cpm — the degraded guard would refuse normal windows and park accounts daily. `ctr` keeps the impressions and clicks sentinels.
- Money is AED-converted pre-flatten with the same `AedRateProvider` as the main feed. `actions`/`action_values` arrays are dropped after flattening (no child tables); keep reading `actions_*`/`action_values_*`. Also dropped: the `no_adset_id`/`no_ad_id` placeholders and the always-zero trial/subscription scalars (conversions are not requested).
- Column hints apply because the table is new: `spend`/`spend_source`/`ctr` Float64, `impressions`/`clicks` Int64, `date_start`/`date_stop` Date. `account_id`/`campaign_id` are deliberately unhinted so they stay text, like `fb___insights`, for cast-free joins.
- **Rollout order:** the first load writes 93 days for every account in one unattended run and can approach the 131k-row vertical-merge exposure. Dispatch Facebook Batch A manually (or watch its first scheduled run), and run `ALTER TABLE travel.fb___insights_country MODIFY SETTING enable_vertical_merge_algorithm = 0, non_replicated_deduplication_window = 1000` as soon as the table appears, before batches B and C load.
- Merge never deletes a stale country row: if a 7-day refresh stops returning a small or `unknown` country slice an earlier run stored, the old row stays. Watch for this in reconciliation; if it matters, switch to replacing per account × date.
- **Not yet consumed.** Question 1001 still reads targeted countries. Before repointing it, reconcile per account × day against `fb___insights` for spend **and** each action total: Meta may not split iOS app-event conversions (SKAdNetwork) by country, in which case only spend/impressions/link clicks should come from this table.

### Google Ads spend completeness (travel `google` dataset)
`travel.google___google_ads` is **ad-grain and does not contain all spend**. `AD_METRICS_QUERY` reads `FROM ad_group_ad`, and Performance Max campaigns have no `ad_group_ad` rows, so their cost never loads. Measured over 90 days against internally attributed revenue, two separate gaps leave ~10% of revenue with no spend counterpart:
- **PMax** — 2 campaigns, 25,477 AED. Present in `google___google_ads_campaigns` (sourced `FROM campaign`) but absent from `google___google_ads`.
- **An unconfigured ad account** — 32 campaigns, 176,192 AED, dominated by hotelsgrab.com (25 campaigns, ~115k sessions). Those campaign ids appear in *no* Google table and are confirmed absent from `fb___insights`, so they are Google campaigns under an account missing from `secrets/google.json`.

`campaign_metrics` → `google___google_ads_campaign_metrics` is what closes the first: campaign-grain, `FROM campaign`, so PMax is included. **Not closed yet** — the table is created by the first successful run, and nothing reads it until question 994's `spend` CTE is repointed at it and the KNOWN GAP caveats come off 993 and 994. It is a **new table, not a change to `ads_metrics`** — `google___google_ads` is read directly by Metabase question 644 *and* by 994's `spend` CTE, so changing its grain would silently move live numbers. Keep both; `ads_metrics` still owns the ad-level status columns that have no campaign-level equivalent.

`customer_clients` → `google___google_ads_customer_clients` closes the second: one `FROM customer_client` query against the MCC, listing every child account with `currency_code`, `time_zone` and `status`. It runs **once per pipeline run, outside the per-account loop**, because it is keyed on the manager account rather than a customer. Check it before adding any account id — the Google pipeline has **no currency normalization at all** (unlike `pipelines/facebook/currency.py`), so a non-AED account would sum straight into an AED total. It may also distinguish an account that was cancelled from one whose sync broke, if Google returns non-`ENABLED` children — unconfirmed until a run shows one.

- **Any new merge table needs `ALTER TABLE <t> MODIFY SETTING enable_vertical_merge_algorithm = 0`** right after its first load — standing policy, see the ClickHouse note under Data Loading Patterns. Don't wait for a size estimate to justify it: `google___google_ads` carries 174k live rows against 277k part rows because delete-marked rows linger, and how fast the campaign-grain table approaches the 131k threshold depends on whether `FROM campaign` emits zero-metric rows for idle campaigns, which only a live run shows (48 campaign-days/day if not, ~400/day if it does — years versus months).
- `conversion_actions` is also `FROM ad_group_ad` and equally PMax-blind. Not fixed.
- `pipelines/subscription_google/` defines its **own** `ads_metrics` and its own `all_sources`, so it does not inherit `campaign_metrics` and carries the same PMax gap.
- The unprefixed `travel.google_*` tables (`google_customer`, `google_ad_group`, `google_ad_group_ad`, `google_ad_group_bidding_strategy`, `google_ad_group_criterion`, `google_ad_listing_group_criterion`, `google_campaign_bidding_strategy`, `google_campaign_criterion`, `google_campaign_label`, `google_click_view`, `google_label`, `google_user_interest`) are **dead, of unknown provenance** — they are `ReplacingMergeTree` while every dlt-written table here is `MergeTree`, and no current pipeline writes them. ### Google campaign names are point-in-time (travel `google` dataset)
`google___google_ads.campaign_name`, `ad_group_name` and `ad_name` are plain columns on a merge table keyed `(account_id, ad_id, date)` with `ROLLING_DAYS = 30` in `pipelines/google/sources.py`. A row keeps whatever name Google reported the last time that date sat inside the 30-day window, so **every date older than the window is frozen**. `ad_name` is blank on 99.1% of rows because Google does not name most ad types, so a rename surfaces as `campaign_name` — and as `ad_group_name`, which is populated, freezes the same way, and is what question 625 breaks out on.
- A marketing rename landed in Google around 2026-10-27/28. Before repair it had frozen 107,014 of 185,415 rows in `google___google_ads` (189 campaigns, 4.61M AED) and 361,807 of 509,796 rows in `google___google_ads_conversion_actions` under names Google no longer uses. Last stale date was 2026-09-28 in the ads table but 2026-10-18 in conversion_actions — the two tables do not share a boundary, so never verify one and assume the other.
- `google___google_ads_campaigns` is `write_disposition="replace"`, rewritten whole every run, so it always holds the current name and is strictly fresher than the metric tables: campaigns that stop spending are never re-stamped at all, so before the 2026-11-05 repair only the replace table knew their new name. **Read campaign labels from it, never from the metric tables.** There is no equivalent current-state table for ad groups. The flip side is that a campaign Google stops returning from `FROM campaign` drops out of the replace table: question 994 degrades to the frozen spend-row name, but question 623 breaks out on the joined column directly, so that campaign's whole history would collapse into one NULL row. Zero campaigns are in that state today (all 283 in `google___google_ads` have a replace-table row).
- Repaired 2026-11-05 by five per-account `google-backfill.yml` dispatches over each account's full history. GAQL returns the entity's **current** name on historical rows and does return rows for long-dormant ads — proven by a probe on account 7798955907 for 2026-08-01..2026-08-31, where stale rows went 5,313 → 0 with row count and distinct ad count both unchanged at 5,468 / 196. A sixth account (`2749505452`, Discounts70) needed no dispatch — all its data is inside the rolling window. Residue after the full repair is 4 rows in the ads table and 18 in conversion_actions: the ads-table four are zero-cost single-impression ad-days, but the conv rows carry **real conversions and value** (up to 3.0 conversions / 17.52) — only their names are stale. dlt's delete-insert merge only deletes keys present in the staging table, so a row Google stops returning keeps its old name forever. Expect a small residue, never exactly 0.
- **`travel.mart_ad_dim_mv` derives Google `app_code`, `vertical` and `target_platform` from this frozen column** and nothing else in the repo says so — it is visible only in `system.tables`. The Google branch computes `argMax(if(match(campaign_name, '^[A-Z][0-9][AIW][A-Z]'), upper(substring(campaign_name, 1, 4)), ''), date) AS app_code`, with `vertical` from letter 4 and `target_platform` from letter 3. The rename was a prefix-convention migration, which is exactly what flips that regex: `WEB - NL - NL #2` fails it, `D1WH - NL - NL #2` matches. So the rename silently misclassified 752 of 3,090 Google ads (24%) as `vertical = 'unknown'`. It reaches a consumer only where one joins `mart_ad_dim` at query time, e.g. question 1000 — `mart_marketing_daily` carries no `app_code`/`vertical`/`target_platform` column and is **not** affected, nor is `mart_ad_spend_daily_mv`, which is ids and metrics only. The backfill heals it on the next hourly refresh (`REFRESH EVERY 1 HOUR OFFSET 5 MINUTE`): blank `app_code` for Google ads goes 842 → 90.
- The 90 that stay blank are not a defect — their *current* Google names genuinely do not match the app-code convention. Post-repair verification should expect 90, not 0, and only **after** the next hourly refresh: `mart_ad_dim` keeps showing the pre-repair figure until then, and `system.view_refreshes` is not readable by the `mcp_ro` role.
- **This decays again and the rolling window cannot reach it.** `argMax(campaign_name, date)` pins each ad's name to its last spend day, so an ad whose `last_seen` falls outside 30 days freezes permanently: 1,327 of 3,090 Google ads (43%) are already outside that window. The next rename re-opens this, and the only remedy is another full-history backfill, not a 30-day one. The durable alternative, deliberately not taken, is to resolve the MV's Google branch from `google___google_ads_campaigns` instead of `argMax`.
- Metabase consumers that must read the replace table, not the frozen column: question **994** (native, `known_campaigns` CTE, `min(campaign_name)` not `any()` since `any()` is nondeterministic under parallel execution) and question **623 "Campaign level"** (MBQL, breakout on the joined `google___google_ads_campaigns.campaign_name`; it is a `pivot`, and `pivot_table.column_split.rows` references the column by the literal name `campaign_name`, which the join preserves). Both were repointed 2026-11-05; **before** that repair 994's window showed 74 campaigns under 106 labels and 623's full history 283 campaigns under 326 labels, and both now sit at 1:1. Question **625 "Ad Group level"** breaks out on `ad_group_name` and has **no** current-state source, so it will drift again. Question 626 breaks out on `ad_id` and question 644 on `account_name` (no account has been renamed) — both unaffected.
- **`google___google_ads_campaign_metrics` starts freezing from 2026-11-06.** It was clean on 2026-11-05 not because it postdates the rename — its earliest row, 2026-10-06, is three weeks *before* it — but because its whole history still sat inside the 30-day window and was re-stamped daily. 2026-10-06 was exactly `today() - 30`; from the next day the oldest day falls out and that table freezes exactly like `google___google_ads`. `campaign_metrics` is absent from `METRIC_SOURCES` in `pipelines/google/backfill.py` and takes no `start_date`/`end_date`, so it cannot be repaired account-scoped through `google-backfill.yml`; it **can** be repaired group-wide through `backfill.yml`, whose `days` input reaches it as `GOOGLE_BACKFILL_DAYS` (`_reusable-etl.yml:120` → `get_days_back()` → `campaign_metrics(days_back=...)`) — but that also re-runs the `replace` resources for the whole group. Settle this before 994's spend CTE is repointed at it.

- **994 "Google Ads daily — base for GUI questions"** (native SQL) holds the join of campaign-grain spend to internally attributed revenue; **993 "Google Ad spend per account (attributed)"** is an MBQL question built on it, so date ranges, filters and groupings stay editable in the query builder. ### Metabase: FB iOS country-wise report (Travel Apps)
Dashboard **73 "FB iOS Ads Country wise Report"** is one pivot card, **1002 "Country wise report (iOS)"** (MBQL, countries as pivot rows, 22 measures), built on the native helper **1001 "FB iOS country base data"**. Same two-layer shape as 994/993 above, and for the same reason: the parts MBQL cannot express live in the helper, everything else stays editable in the query builder. The dashboard Date and Account filters map to the helper's `day` and `account_name` columns, which Metabase pushes down as an outer `WHERE` on the subquery — verified end to end, not assumed.
- **The helper must be SQL because MBQL has no UNION**, and the helper unions two differently-grained sources: Meta spend rows and session-joined revenue rows. Second reason: unnesting `fb___ad_sets__targeting__geo_locations__countries` to get an ad set's targeted country. The `app_code` regex is *not* a reason — question 611 derives the same thing in MBQL with `regex-match-first`.
- **Never put a SQL comment in 1001.** With any `--` comment present, a dashboard-filtered run dies with `It looks like we got more parameters than we can handle` from the ClickHouse JDBC driver, which stops finding the bind placeholders Metabase generates. The unfiltered question still works, so this breaks the dashboard *only* and will not show up when you test the question by itself. Established by elimination: identical SQL fails with comments and passes without them, and question 1003 keeps its comments and is unaffected precisely because nothing filters it. The character-level trigger inside the driver is not understood — do not assume it is apostrophes or question marks, both were tested and neither explained it. Documentation for this query lives in its Metabase description instead.
- `iros_value` takes the **join and exclusion** definition from question **884 "Facebook Revenue iOS"** — `travel___user_sessions_enriched` joined to `travel___conversions_enriched` on `session_id = user_session_id`, `route NOT IN ('push','local')`, `platform = 'ios'` — and deliberately **generalises away 884's own slice**: its `managing_system='d1'`, `app_vertical='hotel'`, six-country and 14-day filters are not carried over. So 1002 unfiltered is roughly **2x** 884 for the same day, because it spans ten app codes where 884 spans one. Filter the dashboard to a single Account and the two match: both convert USD revenue at **3.67**, the rate the business uses — deliberately not the 3.6725 peg the Facebook currency code uses. `INNER JOIN` rather than 884's `LEFT JOIN` — a session with no conversion adds 0 to a `sum`, so the result is identical and the join is cheaper.
- **Attribution is to the session's creation day and the session's country**, not the conversion's. Inherited from 884. A conversion from an old session lands on the old session's day.
- The helper carries **both** a raw `created_at` range and the `toDate(..., 'Asia/Dubai')` one, because **any** `toDate(created_at)` predicate — tz-converted or not — defeats partition pruning on `PARTITION BY toYYYYMM(created_at)`: 36.9M rows scanned against 10.4M. Do not drop either predicate. Note `created_at` is `Nullable(DateTime)` with no timezone and the server tz is already `Asia/Dubai`, so the tz argument is currently a no-op and is defensive pinning; the sorting key is `session_id, vertical, country_code, created_at`, so `created_at` sits 4th and is useless for range pruning on its own.
- Window is `d0-92 AND d0-2`, which is **91 days**. A dashboard Date filter can therefore only **narrow**, never widen — ask for six months and you silently get 91 days. The `app_accounts` map is computed over the full window inside the helper, so account labels stay stable however the dashboard is filtered.
- Grain is **day × account × country**. Question **1003 "FB iOS country base data (ad grain, archived)"** keeps the old ad-grain SQL for the campaign behind a country number — but its revenue is a *different definition* (`travel___reports_report` allocated across ads by spend share), so its numbers do **not** reconcile with 1002's `iROS Value`. It is only "archived" in its name; it is a live card in the same collection.
- Every row's `account_name` comes from an `app_code -> account name` map built off the spend side, 1:1 across all ten iOS accounts — spend rows included, since `ads.account_name` is discarded once the map exists. This is what the Account filter actually filters on. Before the map, revenue-only rows carried `''` and **an account filter silently dropped their revenue**. `min(account_name)` not `any()`, which is nondeterministic in ClickHouse under parallel execution; the cost is that a mid-window Meta account rename relabels the whole window to the alphabetically-first name.
- **Exclusion is per app_code (managing_system × vertical), not per account**, and this is the report's least obvious blind spot. An app code with no iOS Meta spend in the window is dropped: today that is ~75k AED, 7.4% of iOS conversion revenue, led by **M4IC (~31k)**, then M1IH (~26k), M5IC (~13k), M5IH, M4IS, M1IC, M8IC. M4 and M8 **are** configured, spending accounts — only those verticals of theirs are missing. Someone auditing M4 will not find this unless they are told.
- **`MULTI` revenue is zero by construction**, not merely small: revenue rows are keyed on the session's ISO country code, which can never equal the literal `MULTI`. It is ~10.3% of spend (multi-country ad sets ~57.2k AED, plus ~6.6k from ad sets **missing from `fb___ad_sets` entirely**; ad sets present with no geo rows do not occur). The consequence for the number people will quote: the pivot's grand-total iROS of **1.50** is mechanically ~10% below the country-matched **1.67**, because a tenth of the denominator can never have a numerator. Worse, several `WW` ad sets parked in MULTI target the US, so **US iROS is overstated**.
- Only **8 of 70** rows carry spend, and one of those is MULTI — so seven real countries. The rest are revenue-only with blank ratio columns (Metabase's MBQL `/` returns NULL where raw SQL would give `Infinity`). The eye-catching ratios come from countries with a *small* spend row against largely organic revenue — GB 10.4 on 1,356 AED, PH 25.9 on 510 AED — not from the blank ones.
- Pivot grand totals on the ratio measures are **ratios of totals, not averages of per-row ratios** — verified to 14 significant figures. That holds only because all 22 measures are MBQL aggregation expressions; moving a ratio to a post-aggregation custom column would silently turn its total into an average. `pivot_table.column_split.values` holds measure **display-name strings**, so renaming a measure is a two-place edit (the aggregation's `display-name` and that list) and missing the second makes the measure vanish from the pivot.
- `fb___insights` once held physically duplicated rows (one `_dlt_id`, two identical copies), which inflated this report and every other consumer by ~0.2% on spend. Cleaned 2026-11-03 — see the duplicate-insert note under Data Loading Patterns.

## GitHub Actions Workflows
- `google-backfill.yml` runs explicit inclusive date ranges for one account or all accounts/groups. Keep it metric-only: shared `replace` resources must not run for an account subset. Google writers share concurrency group `google-ads-travel`; keep dropdown group options aligned with `GOOGLE_GROUPS`.
- **`google-backfill.yml` has no Slack notifier.** It defines its own five-step job and never uses `_reusable-etl.yml`, so it has no `if: failure()` step at all — *every* failure mode is silent, not just the cancellation case. Watch a dispatch rather than relying on an alert.
- **Dispatch `google-backfill.yml` strictly one account at a time.** `cancel-in-progress: false` reserves only **one** pending slot per concurrency group, so a third queued run cancels the pending one. The victim is not only another backfill: `_reusable-etl.yml` puts the **daily** Google ETL in that same `google-ads-travel` group, so a backfill queued behind a running one can cancel a pending scheduled daily load — and a cancelled job does not fire `if: failure()`, so the day's Google spend would vanish with no alert. (`queue: max` appears in the `concurrency` block of both `google-backfill.yml` and `_reusable-etl.yml:48`; it is not a real GitHub Actions key and is ignored, so do not rely on it for queueing.)
- `.github/workflows/_reusable-etl.yml` — Shared job template all pipelines use
- Daily schedules (UTC): Facebook batches A/B/C 0:00/1:00/2:00 (5:30/6:30/7:30 IST), Subscription Google 2:50 (8:20 IST), Google Ads 3:00 (8:30 IST), Subscription Facebook 3:00 (8:30 IST), GA4 4:30, Google Play 5:10, App Store 6:10, eSIM Facebook 8:30
- Hourly: eSIM Analytics API every hour at :15
- `backfill.yml` — Manual dispatch workflow for historical data loads. Every dispatch runs as a matrix job, one per group, including a single group (a one-element matrix). Its `prepare` step must **never** name its shell variable `GROUPS`: that is a bash special variable holding the caller's group IDs, bash silently ignores assignments to it, and `$GROUPS` then expands to the primary GID — which is why multi-group dispatch was broken from the start and always ran one job with the comma-joined string as the group name. Group names are parsed with a single `jq --arg` call and validated against `^[A-Za-z0-9_-]+$`, because `_reusable-etl.yml` interpolates `inputs.group` straight into `run:` blocks
- `backfill.yml` also takes two optional Facebook-only inputs, both validated in `prepare` and read through `env:` rather than `${{ }}` interpolation: `insights_load_window_days` → `FB_INSIGHTS_LOAD_WINDOW_DAYS` and `dataset_name_override` → `FB_DATASET_NAME`. **The window size is the only lever that keeps a long backfill inside the 6-hour runner ceiling**: the default 8 gives 23 windows per account and each window submits *two* Meta async jobs (core + unique metrics), so a 180-day run over 16 accounts is ~368 job pairs; 20–30 cuts that to 6–9 per account. Accepted range is 1–90: the upper bound exists because a window wider than the backfill collapses `iter_date_windows` to a single request, discarding the per-window checkpoint that makes a long run restartable. Validation is pure glob — `[ -eq 0 ]` returns 2 with a stderr error on a digit string too big for an integer, which an `if` reads as "not zero" and lets through — and note `0*` cannot be the all-zeros pattern, since `case` patterns are globs, not regexes, so it would also reject `08`. `FB_INSIGHTS_LOAD_WINDOW_DAYS` is gated on `contains(inputs.pipeline, 'facebook')`, **not** `== 'facebook'`: `positive_int_env` reads it inside the shared `run_insights_in_windows`, which `esim_facebook` and `subscription_facebook` also reach, so all three honor it. `FB_DATASET_NAME` stays `== 'facebook'` because those two hardcode their datasets; `prepare` rejects the mismatch outright rather than letting the value drop silently. `dataset_name_override` is restricted to `^(fb|fb_smoke_[a-z0-9_]{1,32})$`, matching `resolve_dataset_name`'s `re.fullmatch` so an over-long name fails at the gate instead of after checkout and `pip install`. Match it with bash `[[ =~ ]]`, **never `grep -E`**: grep anchors per line, so `^...$` passes any value whose first line is valid. That shape check is a typo guard, not an injection guard — the value reaches an `env:` entry, never a `run:` block, and `resolve_dataset_name` is the real authority (it also refuses any override when `GITHUB_EVENT_NAME=schedule`). A smoke dataset is a **new** set of merge tables: apply the standing `enable_vertical_merge_algorithm = 0` / `non_replicated_deduplication_window = 1000` ALTERs after its first load. Both inputs flow through the matrix, so a multi-group dispatch sends **every** group to the same smoke dataset — intended for a one-group smoke run, not a production backfill
- **Nothing serializes a backfill against the daily Facebook batches.** For non-`google` pipelines `_reusable-etl.yml`'s concurrency group embeds `github.run_id`, so it is unique per run and never queues; `backfill.yml` has no workflow-level `concurrency` and does not join `daily-facebook-1.yml`'s `facebook-batch-a`. A production-dataset backfill of `d1a` can therefore run alongside daily batch A loading `d1a`, sharing both the destination tables and the `fb_staging___*` merge staging tables — exactly the hazard `google-ads-travel` exists to prevent — and doubling that account's Meta quota draw against a per-process pacing model. `dataset_name_override` sidesteps it, but defaults to production; otherwise dispatch outside 00:00–04:00 UTC
- **`backfill.yml` takes a day count, never a date range**, and `pipeline_name_suffix` embeds `github.run_id`, so dlt state is fresh every dispatch and a re-dispatch restarts at `today() - days`. There is no resume and no way to target an older slice: a smaller `days` just re-does the recent span. A job killed by the 6-hour ceiling is *cancelled*, and `if: failure()` does **not** fire for a cancellation, so the most likely failure of a long backfill is also the silent one — watch the run rather than relying on the Slack alert
- Secrets are base64-encoded in GitHub (DLT_SECRETS, FB_GROUPS, GOOGLE_GROUPS, etc.)

## eSIM Project Pipelines
The esim project uses a separate ClickHouse database (`esim_db`) via the `clickhouse_esim` dlt destination.

- **`pipelines/esim/`** — Analytics Export API pipeline. Manifest-driven: fetches dataset config (watermark fields, strategies, endpoints) from the backend's `/internal/analytics/exports/manifest/` at runtime. Most column types are auto-detected; reviewed additive fields use explicit hints where stable inference matters. Config in `secrets/esim.json`.
- Order analytics remain one row per order.
- **Schema-version gating is on MAJOR, not exact match.** `SUPPORTED_SCHEMA_VERSIONS` in `pipelines/esim/constants.py` records the versions actually *reviewed* here; `manifest._resolve_schema_version` then accepts any **MINOR** of a reviewed **MAJOR** with a loud `SCHEMA DRIFT` warning, and hard-fails an unreviewed **MAJOR** (or a malformed version). Datasets absent from the dict are ungated. Reviewed today: users through `1.2`, sessions through `1.2`, and orders through `1.5`.
  - Rationale: the backend bumps MINOR for additive columns only (1.2, 1.3, 1.4 all were) and dlt never retypes an existing column, so only *new* columns are at stake. Exact matching meant every additive backend field hard-stopped the **whole** hourly run (all datasets, not just orders) until someone edited the set — which is exactly what happened when the backend shipped orders `1.4`. A MAJOR bump can change or drop existing columns, so it stays gated.
  - The highest-risk MINOR addition is a **new money column**: the backend's `to_numeric` sends `Decimal` as a JSON float, so an unhinted one infers as `double`. This is why money fields are pinned in `DATASET_COLUMN_HINTS`; attribution and funnel columns are also pinned where nullability or an initially empty dataset could make inference unstable. On a `SCHEMA DRIFT` warning, check the new fields and add any necessary hints before recording the version as reviewed.
  - Order version history: `1.2` added `subtotal_eur`/`profit_eur`/`item_count`/`distinct_plan_count`/`is_cart`; `1.3` added `payment_method`/`stripe_account_slug`/`stripe_account_acct_id`; `1.4` added `support_resolution` and made wallet-compensated orders export `status='refunded'` — nothing reads refunds today, but if that changes, split real Stripe reversals (`support_resolution=''`) from wallet credits (`'compensated'`).
  - Sessions `1.2` adds the four funnel booleans (`plans_viewed`, `plan_added`, `checkout_viewed`, `purchased`) and their nullable `*_at` timestamps. Keep explicit bool/timestamp hints for these fields so empty early-stage data cannot cause unstable inference.
  - Column hints are selected by the manifest's dataset version through `DATASET_COLUMN_HINT_MIN_VERSIONS`; keep that map updated so a connector-first deploy never declares future non-null columns against an older backend export.
  - The backend mirrors this contract in `analytics_export/views/manifest.py` and pins the version in `analytics_export/tests/test_orders.py`, so a bump there fails a test that names this file.

## PostgreSQL Replication Pipeline
`pipelines/pg/` handles logical replication from remote PostgreSQL sources into ClickHouse, used for dashboard and travel datasets. This is distinct from the API-based pipelines.

### Inline ad CPC in USD (`travel.inline_ad_logs`)
- `cpc_price`/`cpc_currency` arrive in many currencies and are loaded **untouched**. `pipelines/pg/travel/fx.py` adds only `cpc_price_usd`; chart that. No rate columns are stored, deliberately: the rate is `cpc_price_usd / cpc_price` and its day is the UTC date of `created_at`. Every fetched rate is kept in `inline_ad_fx_usd_rates` for audits.
- Rates come from **currencyapi.com** (v3, USD base), keyed by `sources.currencyapi.api_key` in `.dlt/secrets.toml` / the `SECRETS` GitHub secret. A USD-only run needs no key and makes no request.
- The job runs every 45 min, but the free plan is ~300 requests/month, so every fetched snapshot is cached in the ClickHouse table `inline_ad_fx_usd_rates` (one row per kind/day/currency; ReplacingMergeTree on `fetched_at`, read with `FINAL`). A past day's `historical` is fetched once; today's `latest` is reused for 6h. Expect ~5 requests/day. Never fetch per run.
- The cache is written **the moment a snapshot is fetched**, not with the dlt load. Don't move it into dlt resource state: that only commits with a successful load, so every failed run would throw away rates it had already paid for. A rate is correct whether or not the load that fetched it succeeds. Lookups are by **exact day, with no age window**.
- An API failure (network, 401, 429 quota) **raises**: nothing commits and the `created_at` watermark stays put, so the next run retries. This blocks the rest of the travel sync until resolved. A NULL would be permanent, because rows are never re-read. A currency code missing from a valid snapshot only NULLs that row's `cpc_price_usd` (with a warning).
- New rows only; rows loaded before this change have NULL `cpc_price_usd`.
